# Project Integration Test Evidence

## Purpose

Use this skill when a task mentions integration tests, component/system/e2e test evidence, test artifacts, `temp/`, CI artifacts, test run receipts, or cross-project testing standards.

The goal is simple: every integration test run must leave enough local evidence for a human or agent to understand what ran, where it ran, what passed or failed, and which files prove it.

## Required Standard

Every owning subproject with integration tests should write evidence to:

```text
<subproject>/temp/integration-test-runs/<run-id>/
```

Minimum files:

```text
summary.json
command.txt
stdout.log
stderr.log
env.json
artifacts/
```

Recommended project entrypoints:

```bash
bun run test:integration
task test:integration
```

Use the project language and existing runner. Do not add a parallel testing framework just to create evidence.

## Summary Schema

`summary.json` must be generated by a project script, CLI, or application service. Agents should not hand-write this metadata file as the official workflow.

Required fields:

- `schema_version`: `yeisme.integration_test_evidence.v1`
- `project`: owning project path such as `agent/ordo`
- `run_id`: unique run id
- `layer`: usually `integration`; may be `component`, `system`, or `e2e` when that is the actual layer
- `command`: real command that was run
- `status`: `passed` or `failed`
- `exit_code`
- `started_at`, `finished_at`, `duration_ms`
- `evidence`: paths to stdout, stderr, command, env, and artifacts
- `redaction`: whether redaction was enabled and which policy was used

## Workflow

1. Route to the owner:
   - Root `openspec/` only defines repository-wide policy and handoff.
   - Concrete runner/package/Taskfile/CI/test changes go into the owning subproject OpenSpec change.
2. Inspect the existing test stack:
   - Bun/TypeScript: package scripts and current `bun test`/Vitest setup.
   - Go CLI: Taskfile, Go `testing`, and `testscript` where command e2e is involved.
   - Backend/service: docker compose, Testcontainers, migrations, ports, and cleanup.
3. Add or update the integration entrypoint:
   - `bun run test:integration` for Bun/TypeScript projects.
   - `task test:integration` for Go/Taskfile projects.
4. Ensure the wrapper always writes evidence, including on failure.
5. Redact output before persistence.
6. Add tests for evidence creation and failure behavior.
7. Run the real integration command and inspect `temp/integration-test-runs/<run-id>/`.

## Subagent Handoff

For Codex feature delivery, keep implementation and verification in separate
contexts:

1. One implementer owns tracked production code and all related test/fixture
   edits for the bounded feature.
2. A separate test engineer runs the existing integration/component/system/e2e
   entrypoint and writes evidence under `temp/integration-test-runs/<run-id>/`.
3. The root receives `summary.json`, the command, exit code, evidence paths, and
   a compact failure signature. Do not paste full `stdout.log` or `stderr.log`
   into the root task unless a small excerpt is required to choose the next
   route.
4. A deterministic product failure returns to the same implementer as a compact
   failure packet. Environment flakes stay with the test engineer for
   classification and do not authorize tracked-file edits.
5. The test engineer records tracked-file state before and after the run. Any
   tracked source, test, fixture, snapshot, config, or lockfile change
   invalidates independent verification.

Classify failed verification as `product`, `test`, `environment`, `flaky`,
`permission`, or `ambiguous` in the worker envelope. This is a handoff field,
not a new required `summary.json` schema field.

This separation prevents frequent integration runs from exhausting the root or
goal context while preserving reproducible evidence on disk.

## Redaction Rules

Evidence must not contain:

- secrets, tokens, cookies, passwords, private keys
- `Authorization` headers
- raw prompts
- hidden system prompts
- provider payloads
- complete chain-of-thought
- private tool parameters

When preserving request/response fixtures, save redacted fixtures only and record that in `summary.json`.

## Validation

Root design validation:

```bash
openspec validate --all --strict
```

Subproject implementation validation examples:

```bash
cd agent/ordo
bun run test:integration
find temp/integration-test-runs -maxdepth 2 -type f | sort
```

## Boundaries

- Do not store evidence in repository root `temp/` for a subproject test.
- Do not commit test evidence; `temp/` should be ignored except optional `.gitkeep`.
- Do not redefine all tests as integration tests. Unit tests do not need this evidence path.
- Do not bypass the AI Native CLI output contract when evidence comes from CLI commands.
- Do not implement subproject test runners from the root context; enter the owning subproject first.
- Do not let a test engineer modify tracked source, tests, fixtures, snapshots,
  or configuration while acting as the independent verifier.
